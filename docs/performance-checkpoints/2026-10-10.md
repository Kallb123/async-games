## Summary

1. **Warm server reads are fixed.** Game API `server_total` is 40 ms (`entry`,
   n=2) and 38 ms (`refresh`, n=6), against the 271 ms untagged median. The
   dashboard on `refresh` (n=3) is 58 ms against 598 ms. The player-directory
   cache and the projection did what the plan predicted when the instance is
   warm.
2. **Mongo query plans are not the problem.** Every dashboard and game read uses
   an index and examines at most 11 keys or documents. No index or projection
   work is needed.
3. **Cold function instances now dominate.** A dashboard `entry` takes 6,044 ms
   at the median, 3,616 ms of it outside our handler and 2,319 ms inside it. Of
   that, 1,301 ms is `mongo_query` for three reads the explain times at 1 ms or
   less.
4. **`/` is still rendered on a function.** The Clerk handshake and the service
   worker are off the cold path, but the build still marks `/` as dynamic.
   `TTFB_request` is 2,826 ms. A cold home open therefore pays two cold
   functions in series.
5. **The next work is not what the plan ranked next.** Serving `/` statically
   and the cold-instance checks come ahead of the shared memory cache and
   prefetch. The plan's delivery sequence is reordered accordingly.

## Mongo query plans are not the problem (confirmed by explain)

From `npm run perf:explain` against production (full report below). The sample
was the player in the most live games and the largest live game.

- Every dashboard and game read uses an index. At most 11 keys and 11 documents
  are examined (the completed results, which is the `limit + 1` the dashboard
  asks for). Each read takes 0–1 ms.
- The `{ playerIds: 1, endedAt: -1 }` explain that Phase 2 said was owed is now
  done: `LIMIT > PROJECTION_SIMPLE > FETCH > IXSCAN playerIds_1_endedAt_-1`, 11
  examined, 11 returned.
- Live game documents are 13–32 KB (Realm Arena 13 KB, Train Time 21 KB, Fires
  Out 32 KB). Production has only three live games, one of each of those. A
  projection of Realm Arena's `commandHistory` would save almost nothing, so
  that idea is dropped.
- So the game route's `mongo_query` p95 (1,228 ms untagged) is not the query.
  It is connection setup on a new instance, as the next section shows.
- Caveat: the explain's milliseconds are the server's execution time. The app's
  `mongo_query` span also holds the network round trip and Mongoose hydration.
  That gap is picked up under "Network distance".

## Cold function instances now dominate (likely; n=4 but consistent)

The dashboard `entry` rows (n=4) all landed on fresh instances: `mongo_connect`
is 296 ms at the median, where a warm instance reports 0.

| `/api/dashboard`, `entry` (n=4) | Median (p75 / p95), ms |
| --- | ---: |
| `api_total` (`fetch()` to last byte) | 6,044 (6,610 / 6,648) |
| `api_network` (outside our handler) | 3,616 (4,126 / 4,284) |
| `server_total` | 2,319 (2,418 / 2,515) |
| of which `mongo_connect` | 296 (516 / 535) |
| of which `mongo_query` | 1,301 (1,539 / 1,661) |
| of which `names` (a cache miss) | 314 (319 / 356) |
| of which `player_directory` | 376 (377 / 415) |

(The span medians do not add up to the totals. They are medians of different
spans over four samples, and some spans nest.)

On a game `refresh` the same pattern shows in the tail (n=6): `api_network` is
117 ms at the median and 2,562 ms at p75, `server_total` is 38 ms and 1,177 ms,
`mongo_connect` is 0 ms and 377 ms. One `session_retry` cost 3,076 ms (also a
game `refresh`).

- **Platform cold start is the larger half (likely).** `api_network` is the time
  between sending the request and the first byte, less `server_total`. A median
  of 3.6 s there is time spent before our handler runs: the platform starting
  the function, module initialisation and routing.
- **Module size is not an obvious cause (confirmed, production build of
  `a90016b`).** `/api/dashboard` and `/api/game/[gameid]` each trace to about
  6 MB, about 1 MB of it our own chunks. Mongoose is 1.6 MB, Next 1.4 MB and the
  MongoDB driver 1.1 MB. The 3.6 s is therefore mostly the platform, not the
  bundle.
- **The 1.3 s of Mongo time is the pool (likely; the settings are confirmed in
  code).** `dbConnect` (`src/utils/mongodb/mongodb.ts`) passes only
  `bufferCommands: false`. The driver (mongodb 7.2.0) opens pool connections on
  demand and `maxConnecting` defaults to 2. Three reads issued in parallel on a new instance therefore
  wait on connection handshakes two at a time, though the explain shows each
  takes 1 ms or less once connected.
- **Per-instance caches are empty on a new instance (confirmed in code).** That
  is why `names` misses on `entry` (314 ms) but not on `refresh` (0 ms), and
  why the player-directory cache cannot help the first request on any instance.

## The cold document (confirmed for the phases, n=4)

`/` TTFB phases, median (p75 / p95), ms:

| Phase | Median | p75 | p95 |
| --- | ---: | ---: | ---: |
| `TTFB_cache` (= `sw_startup`) | 77 | 83 | 152 |
| `TTFB_dns` | 0 | 0 | 0 |
| `TTFB_connection` | 0 | 0 | 0 |
| `TTFB_waiting` | 37 | 40 | 55 |
| `TTFB_request` | 2,826 | 2,843 | 2,944 |

- **The Clerk handshake is off the path.** `TTFB_waiting` is 37 ms, which leaves
  no room for a redirect pair, and the middleware matcher no longer covers
  pages.
- **The service worker is off the path.** The 77 ms start-up is the worker
  waking, with navigation preload sending the request in parallel.
- **DNS and connection are 0 ms.**
- **What is left is the render.** `TTFB_request` is 2,826 ms, and `/` still builds
  as `ƒ (Dynamic)`. `src/app/page.tsx` calls `signedInHint()`, which reads
  Clerk's `__client_uat` cookie with `cookies()` (Phase 1.1c). `/join`,
  `/login/[[...rest]]` and `/lobby/[inviteId]` are also `ƒ`.
- **So a cold home open pays two cold functions in series:** the page render
  (about 2.8 s) and then `/api/dashboard` (about 6 s). That is the same order as
  cold `dashboard_usable` (6,707 ms median, 10,751 ms p75), whose samples are
  mostly from before the change.
- Static routes are fast: `/settings` TTFB is 240 ms at the median (n=26).
- Warm navigation home has the same cause. `navigation` on `/` is 183 ms at
  the median but 1,357 ms at p75 and 3,565 ms at p95 (n=41), because each warm
  navigation home waits on a server render before the dashboard can mount.
- The `TTFB_*` phases appear only on `/` so far (n=4). Other routes have no
  phase data yet.

## Network distance (likely)

- Warm reads that the explain times at 1 ms or less take 14–40 ms as the
  app's `mongo_query` span: 14 ms (game `refresh`), 17 ms (game `entry`), 23 ms
  (dashboard `refresh`) and 40 ms (Fires Out, untagged).
- Warm API calls spend about 104–145 ms in `api_network` beyond server time for
  a body of about 2 KB: 104 ms (game `entry`, n=2), 117 ms (game `refresh`,
  n=6) and 145 ms (dashboard `refresh`, n=3).

Both are what a function in a different region from the database, or from the
players, looks like. This is inference. Check that the Vercel function region
matches the Atlas region and is near the players. `vercel.json` sets no
`regions`, so the project default applies.

## Gaps in the instrumentation

1. **The admin report needs a `since` cut-off.** The window is hard-coded to
   seven days. Either add a `since` parameter, or stamp each sample with the
   deploy commit, so that a checkpoint can compare before and after. Until then
   a clean post-#892 window does not exist before about 2026-10-16.
2. **`game_usable` is still not measured on its own** (gap 4 from 2026-10-09).
   Mark it when the controls first accept input, or drop it.
3. **Attribution sample sizes.** The CLS, LCP and INP part rows have n=1–3. They
   need a clean window before they can pick a region to fix.
4. **Untagged server-span rows mix eras.** A row with a blank Request column
   holds samples with no `entry`/`refresh` tag. These are everything recorded
   before #892, plus any from a client still running an older bundle (likely,
   for installed apps). Read them as the old baseline, not as the current app.
   The exceptions are `server_names`, `server_kb_worlds` and
   `server_unread_chat`, which did not exist before #890: any sample in those
   rows is from after it.

## Recommended next steps

In order. The plan's delivery sequence follows this order and names the section
that carries each design.

1. **Serve `/` as a static page** (new plan item, Phase 1.1e). Drop the server
   cookie read. Decide dashboard or landing in the browser before first paint,
   from `__client_uat` (Clerk's script sets it, so it is readable from
   `document.cookie`), with a tiny inline pre-paint script plus CSS, and let
   Clerk decide once it has loaded. This removes one cold function from every
   cold home open, and the server render from every warm navigation home
   (`navigation` p75 1,357 ms, p95 3,565 ms). It is being implemented on a
   separate branch now. `/join` and `/login` are candidates for the same
   treatment later.
2. **Cold starts: platform settings, no code.** Check whether Vercel Fluid
   compute is enabled for the project (`vercel.json` does not set `fluid`).
   Check the function region against the Atlas region.
3. **Mongo pool on a new instance.** Set `minPoolSize` and/or `maxConnecting`
   in `dbConnect`'s options, and measure with `server_mongo_query` on `entry`.
   Also, the dashboard runs `unread_chat` and `kb_worlds` after
   `player_directory`, but they only need `games`, so they could run alongside
   it (a small saving).
4. **Admin report `since` filter.** Cheap, and it unblocks every later
   comparison.
5. **Then as planned:** replace Moment.js (Phase 3.8), the shared in-memory
   cache and intent prefetch (Phases 1.3 and 1.4), and CLS and INP once
   attribution has samples. A dashboard prefetch also warms the API instance
   before the tap, which makes it more valuable than it was ranked.
