# Performance checkpoint — 2026-10-09

The first seven-day baseline from the Phase 0 telemetry in
[`loading-performance-plan.md`](../loading-performance-plan.md). The raw admin
report is reproduced verbatim at the bottom so later checkpoints can be compared
against it. Everything above it is analysis. Where it says "confirmed", the code
or the build shows it. Where it says "likely", it is an inference from the
numbers that the next round of instrumentation needs to prove.

- Window: 2026-10-02T05:36Z → 2026-10-09T05:36Z (7 days), 7,882 samples, 162
  metric/route pairs.
- Code at the time: `main` @ `646da11`, Next 16.2.4, `@clerk/nextjs` 7.2.9. None
  of Phases 1–4 has shipped: dashboard rows still `router.push`, and
  `useRefreshableData` has no cache.

## Summary

1. **Every target in the plan is missed, and the cold journeys are the worst by
   a long way.** Dashboard → board (warm) is 1.3 s median and 2.5 s p75, against
   a 1 s target. Home → actionable dashboard is 1.7 s (warm) and 6.1 s (cold)
   median, with a 10.5 s p75 cold, against a 1.5 s warm target.
2. **The largest single cost in the report is the document's TTFB, which comes
   before any of our code runs.** Home is 3.4 s median and the game route 1.7 s.
   The TTFB is bimodal on every route, static ones included: a cluster near
   ~0.25 s and another at 4–6 s. The plan's links, cache and prefetch
   (Phase 1.2–1.4) do nothing for it. It needs diagnosing first (see "Cold loads" below).
3. **On a warm game entry, the client-side API fetch is the biggest piece, and
   it drives the tail.** It accounts for about 0.6 s of the 1.3 s median and
   about 1.7 s of the 2.5 s p75. Phase 1 as planned targets exactly this.
4. **Most of the server time on both reads is the Clerk name lookup, not
   Mongo.** It is about 210 ms of the game API's 270 ms median, and about 280 ms
   of the dashboard's 590 ms. It is also paid again on every poll. This answers
   plan decision 5: yes, cache it.
5. **Two problems the plan doesn't name.** CLS is poor (> 0.25) at p75 on every
   product route except Settings. INP on the Realm Arena board is 416 ms at p75.
6. **Art is not the bottleneck today.** Image load is p95 < 350 ms on every route
   with data. On the game route, LCP follows the data arriving, not the images.

## Server spans

Medians (p75 / p95), in ms. The spans come from `Server-Timing` and are
recorded on **every** fetch, including polls and push refreshes, not only on
entry. That is why there are 580 game API samples against roughly 90 board
loads (about six refreshes per visit).

| Span | `/api/game/:id` (Realm Arena, n=580) | `/api/dashboard` (n=120) |
| --- | --- | --- |
| auth | 1 / 6 / 21 | 3 / 15 / 21 |
| mongo_connect | 0 / 0 / **288** | 0 / 0 / **367** |
| mongo_query | 37 / 97 / **1,221** | **238** / 404 / 1,101 |
| Clerk names | **212** / 314 / 420 (`response`) | **277** / 360 / 423 (`player_directory`) |
| reactions / achievements | 12 / 0 | — |
| response_build | — | 1 / 2 / 9 |
| unaccounted | ~20 | **~70** (`unreadChatCounts`, `kingdomBuilderWorlds` are untimed) |
| **total** | **270** / 442 / 2,133 | **591** / 776 / 1,977 |

- **Clerk is the biggest span on both reads (confirmed).** The game route's
  `response` span is `CreateDataResponse`, and in Realm Arena that is
  `userIdListToNamesAndMap`, which is a Clerk `getUserList` call, plus a pure
  `gameStateToModel`. The 212 ms is almost all Clerk. `usersById` has no
  caching, so every poll pays it again and counts against Clerk's Backend API
  rate limit.
- **Cold functions are 5–25 % of API calls.** `mongo_connect` is 0 at p75 but
  about 300 ms at p95.
- **The dashboard query reads far more than it shows (confirmed).** It loads
  every live game as a full Mongoose document — every Realm Arena
  `commandHistory` included — just to build summary rows. It also loads every
  completed result the player has ever had (`completedGameResults`: no limit, no
  projection). The plan said to paginate "if measurement confirms that is
  occurring". It is.
- **The Realm Arena `findOne` has a long tail: 37 ms median, 1.2 s p95.** It
  reads the whole document, including the full `commandHistory`, although the
  response only needs its length and last id. Measure the document sizes
  (`Object.bsonsize`) before choosing a projection. The tail may instead be the
  first query on a freshly opened connection.
- Train Time (n=5): 1,019 ms total, with `mongo_connect` at 228 ms median — a
  rarely played game lands on a cold function almost every time. Too few
  samples to act on.

## Cold loads: the TTFB problem

| Route | Build | TTFB median | p75 | p95 | n |
| --- | --- | ---: | ---: | ---: | ---: |
| `/` | dynamic | 3,370 | 5,043 | 6,432 | 90 |
| `/games/realmarena/[gameid]` | dynamic | 1,706 | 3,606 | 5,325 | 104 |
| `/newgame` | **static** | 4,701 | 5,639 | 7,153 | 12 |
| `/newgame/realmarena` | **static** | 240 | 4,919 | 6,432 | 8 |
| `/settings` | **static** | 240 | 402 | 5,044 | 37 |
| `/login` | dynamic | 4,056 | 5,199 | 5,808 | 4 |

FCP follows TTFB within about 0.2 s on every route, so once the HTML arrives the
browser paints promptly. **The time is lost before the first byte.** Static
routes, served from the CDN with no render at all, also show the 4–6 s cluster.
So the slow cluster is not page rendering. It is something on the path of every
document request. In order of likelihood:

1. **The Clerk handshake.** `clerkMiddleware()` matches every page. On a
   document request whose session JWT has expired — which it has once the app
   has sat idle for over a minute — Clerk answers with a redirect to its
   Frontend API and back before the page is served. This fits the pattern:
   `/` and push deep links are opened after idle time and are slow, while
   `/settings` loads are mostly reloads during active use and are fast.
   Nearly every page authorises on the client (`useAuthGuard`) anyway. The only
   server component calling `auth()` is `src/app/page.tsx`.
2. **Service-worker startup.** `public/sw.js` handles every navigation
   (network-first), but it does not enable **navigation preload**. A navigation
   therefore waits for the worker to boot before its request is even sent —
   often hundreds of ms on a cold phone.
3. **Middleware / function cold start** for the dynamic routes, and
   radio/DNS/TLS setup on a phone just woken.

The data can't split these yet: the `TTFB` metric is a single number. See the
first instrumentation gap.

## Gaps in the instrumentation

Fix these before the next checkpoint. Without them, the Phase 0 exit criterion
("attribute the median and p75 game-entry time") cannot be met.

1. **TTFB has no breakdown.** Report the `web-vitals/attribution` phases
   (`waitingDuration`, `cacheDuration`, `dnsDuration`, `connectionDuration`,
   `requestDuration`) and the navigation entry's `workerStart`. Also count Clerk
   handshakes: the return leg carries `__clerk_handshake`.
2. **`response_bytes` is effectively missing (2 samples).** The host strips
   `Content-Length` once it compresses the body. Read the API request's
   `PerformanceResourceTiming` instead (`encodedBodySize`, `transferSize`). The
   same entry gives `requestStart` → `responseStart`, which separates network
   from `server_total`.
3. **Server spans are mixed across entry and refresh.** Tag each sample as the
   entry fetch or a later refresh. That makes "what did the entry cost?"
   answerable, and it measures polling load separately.
4. **`game_usable` is `game_board_painted`.** Both are marked in the same frame
   (`useGameData`), so "usable" is never measured on its own. Either mark it when
   the controls first accept input, or drop it.
5. **About 70 ms of the dashboard is untimed.** Time `unreadChatCounts` and
   `kingdomBuilderWorlds`.
6. **Session-retry count.** Record when `fetchWithSessionRetry` had to refresh
   the token, to test the cold-entry hypothesis above.
7. **`source: 'deep-link'` is accepted by the API but never sent.** A push →
   game load can't be told from a PWA relaunch.
8. **Sample sizes.** Only `/` and the Realm Arena board have enough samples
   (n ≥ 40) to decide anything. Every other route is anecdotal this week. Realm
   Arena dominates the game traffic, so a light game hasn't been measured
   meaningfully.

## Recommended next steps

In order. Each is small and reversible, and each should be compared with this
checkpoint when the next one is taken. The plan's delivery sequence now follows
this order, and each step names the plan section that carries its design.

1. **Close instrumentation gaps 1–6.** They are cheap, and they decide items 2
   and 4.
2. **Cold TTFB.** Enable service-worker navigation preload (safe and
   self-contained). If the handshake is confirmed, narrow the
   `clerkMiddleware` matcher to the routes that read auth on the server: the
   API, and `/` unless its server-side guess goes. This is a security-relevant
   change, so it needs a `locksmith` pass. Consider making the game routes
   static shells, since their pages are pure client components. (Plan
   Phase 1.1.)
3. **Short server-side Clerk directory cache** (plan Phase 2, "Cache the
   player directory on the server"), with a stated
   rename-staleness bound. It should take the game API from about 270 ms to
   under 100 ms and the dashboard from about 590 ms to about 300 ms.
4. **Plan Phase 1.2–1.4 as written:** linked rows, a user-scoped in-memory
   stale-while-revalidate cache, and intent prefetch. It remains the right fix
   for warm entry, where the data fetch is the largest step and the tail.
5. **Dashboard query:** project the live games' summary fields, and bound the
   completed results. (Plan Phase 2, "Make the dashboard read only what it
   shows".)
6. **Replace Moment.js** with a shared `Intl` helper. (Plan Phase 3.8.)
7. **CLS and Realm Arena INP** as their own items, starting with attribution.
   (Plan Phase 3.9 and 3.10.)
