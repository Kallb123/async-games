taken against [`loading-performance-plan.md`](../loading-performance-plan.md)
and compared with the [2026-10-09 baseline](./2026-10-09.md) and the
[2026-10-10 partial](./2026-10-10.md). The raw admin report is reproduced
verbatim at the bottom. Everything above it is analysis. Where it says
"confirmed", the code or the numbers show it directly. Where it says "likely",
it is an inference that the next round of instrumentation needs to prove.

- Window: 2026-10-10T23:00Z → 2026-10-19T19:22Z (9 days), 17,782 samples, 417
  metric/route/request/region rows. **From build: any build.**
- Code at the time: `main` @ `4ba0a86`. Everything the plan lists as shipped is
  in: the cold document (1.1a–d), static `/` (1.1e, #898), links (1.2), the

  in the project settings after the 2026-10-10 checkpoint.

  one was clean and nothing since has changed a read.

## How the window was chosen, and what it lets in

The last loading change, #903, merged at 20:53Z on 2026-10-10. The window
starts at 23:00Z so the deploy had settled. It filters by when a sample
arrived, not by `build`. About eighteen deploys (mostly Realm Arena) followed
#903, so the report's "from build" list, which offers the ten newest builds,
no longer reaches back to the first one after it. (The route accepts any build
time as `?build=`, so the API could have been asked directly.)

So a client still running a pre-#903 bundle, such as an installed app that
hadn't updated yet, can be in this window. Two things limit that:

- Every server-span row carries an `entry` or `refresh` tag. None is untagged,
  so nothing older than #892 (2026-10-09) reported here.
- The cache and prefetch metrics (`data_cache_*`, `data_prefetch`) exist only
  from #900 on. They appear on every route that has them.

The report also mixes the two Realm Arena boards. #915 (2026-10-15 08:56Z) made
the 3D board the one players see, so the board's INP, CLS and LCP rows hold
about four days of the SVG board and about four of the 3D one.

## Summary

1. **The cold document is fixed.** `/` TTFB is 371 ms median and 549 ms p75,
   against 3,370 and 5,043. The game route is 154 and 258, against 1,706 and
   3,606. Both meet the Phase 1.1 exit (p75 under 1 s), and the 4–6 s cluster
   is gone from both.
2. **The warm dashboard is fixed.** Warm `dashboard_usable` is 463 ms median and
   822 ms p75, against 1,666 and 3,231. That meets the 1.5 s p75 target.
   Navigation home is 130 ms median and 182 ms p75, against 236 and 1,697.
3. **The cold dashboard has not moved, and something new is waiting.** Cold
   `dashboard_usable` is 6,222 ms median, against 6,145 in the baseline,
   although TTFB fell by 3 s. Between Clerk loading and the data arriving there
   are about 4.9 s, and the dashboard API accounts for about 0.65 s of that.
   The rest is tightly grouped, which looks like a fixed wait. That points at
   the five-second bound on the session confirmation (likely).
4. **The board's tail is the entry API call on an idle instance.** Warm
   `game_board_painted` is better at the median (1,138 against 1,297 ms) but
   worse at p75 (3,610 against 2,536 ms). A game `entry` call is 1,275 ms
   median and 4,580 ms p75. Its p75 is split about evenly between time outside
   our handler and time inside it.
5. **Warm server reads stay fixed at scale.** A game `refresh` is 43 ms of
   server time (n=699), against 270 ms in the baseline. A dashboard `refresh`
   is 29 ms, against 591 ms.
6. **Two costs are now worth fixing that weren't visible before:** the name
   lookup misses on almost every `entry` (about 245 ms each time), and about one
   board poll in seven needs a session retry that costs 3.4 s.
7. **CLS and INP are not fixed.** Neither has had its Phase 3.9 or 3.10 fix
   yet. Board INP p75 improved from 416 to 280 ms.

  (duration, and whether it timed out). See the gaps.

The dashboard has the same shape: `server_total` is 29 ms on `refresh` and
420 ms (2,241 p75) on `entry`. Its `mongo_query` is 15 ms against 115 ms (1,569
p75), and `names` 0 against 244 ms. Train Time's `entry` (n=13) matches.

- **Fluid compute helped the median (likely).** `entry` `mongo_connect` is 0 at
  the median, so most entries landed on an instance that already had a
  connection. At 2026-10-10 every `entry` sample was on a new instance.
  `api_network` on `entry` is 271–277 ms at the median, which meets the
  cold-instance exit.
- **One entry in four still finds a cold instance.** `api_network` p75 is
  2.1–2.3 s, and `mongo_connect` p75 243–268 ms. That is the platform starting a
  function, which no code here changes.
- **The name cache misses on almost every entry (confirmed).** `names` is
  243 ms at the median on `entry` (n=74), on instances that *do* hold a Mongo
  connection. So the instance survived, and the cached names had expired. The
  cache keeps names for 5 minutes. A player opening the app after a quarter of
  an hour finds them all expired, on any instance. The fix is cheap, and
  removes about 245 ms from every game and dashboard `entry`: answer from a
  stale entry at once and refresh it after the response (`after()`), with a
  much longer hard expiry. Names change rarely, and the rename paths already
  drop their entry.
- **The first query after idle is slow on a warm instance (likely).**
  `mongo_query` on `entry` is 362 ms at the median for one read, against 24 ms on
  `refresh`, with the connection already open. A function frozen between
  requests also freezes the driver's heartbeat, so the first command after a
  long freeze may wait on a socket the pool has to replace, or on server
  selection. The span doesn't separate checking a connection out from running the
  command, so this can't be proven yet.
- **The region move did not visibly shorten the warm path.** Warm
  `api_network` is 167–170 ms, against 104–145 ms at 2026-10-10 in `lhr1`.
  Warm game `mongo_query` is 24 ms against 14 ms, and the dashboard's 15 ms
  against 23 ms. Those small n's don't show a change either way. What's left is
  likely per-invocation platform overhead plus the phone's round trip, which the
  report can't separate.

## Session retries cost 3.4 s on one board poll in seven (confirmed)

`session_retry` is reported when a request was refused with a 401, the session
token was renewed (bounded at 5 s), and the request was sent again after a
fixed 1 s wait.

| Route | Request | Retries | Calls | Rate | Retry cost, median (p75) |
| --- | --- | ---: | ---: | ---: | ---: |
| Realm Arena | `refresh` | 105 | 686 | 15% | 3,448 (4,785) |
| Realm Arena | `entry` | 3 | 80 | 4% | 3,074 |
| `/` | `refresh` | 4 | 69 | 6% | 5,062 |
| `/` | `entry` | 2 | 59 | 3% | 2,354 |

- Most are board `refresh`es. That fits a tab coming back to the foreground
  with a token that expired while it was hidden. The refetch goes out at once,
  is refused, and then waits for the renewal.
- After the 1 s wait, about 2.4 s at the median is left for the 401 and the
  renewal. So Clerk's `getToken({ skipCache: true })` itself takes about 2 s on
  these phones. That fits the cold home wait above.
- **The fix:** renew before refetching on `visibilitychange`, rather than
  letting the refetch be refused. The 401 round trip and the fixed 1 s wait both
  go.

## Cache and prefetch (Phase 1.3/1.4)

| Route | `data_cache_hit` | `data_cache_miss` | Hit rate | Hit age, median (p75) |
| --- | ---: | ---: | ---: | ---: |
| `/` | 18 | 64 | 22% | 2,826 (3,995) |
| Realm Arena | 9 | 102 | 8% | 677 (1,876) |
| Train Time | 5 | 15 | 25% | 1,993 (6,504) |
| Fires Out | 3 | 2 | 60% | 1,838 (2,094) |

- **Board hits are mostly prefetches (likely).** Realm Arena's hits are 677 ms
  old at the median, which is a prefetch just before the tap, not a revisit.
- **Prefetch-used rate: at most about half.** There were 33 `data_prefetch`
  samples and 17 board hits. Some hits are revisits, so the true rate is lower.
  The report can't link a hit to the prefetch that filled it.
- **`data_prefetch` takes 381 ms median and 543 ms p75.** A tap usually follows
  a press within 100–200 ms, so a prefetch started on press is mostly still out
  at the tap. It saves only the remainder, and the board joins it rather than
  asking again. That's working as designed: the press-start prefetch overlaps
  the route change.
- **The cache can't help the journeys that matter most.** Players mostly arrive
  at a board from a push (a document load, so an empty cache) or after an idle
  spell longer than the 30 s life of an entry. A hit rate of 8–25% is that
  limit, not a defect.
- Whether a cached paint meets the 200 ms revisit target is still unknown (see
  the gaps). Fires Out's warm `first_data` of 106 ms (n=5, three hits) is
  suggestive.

## Gaps in the instrumentation

1. **The session confirmation isn't timed.** Report how long
   `confirmSession`'s `getToken()` took, and whether it hit the 5 s bound, as a
   sample of its own. Until then the cold home wait is inference.
2. **Milestones aren't split by cache hit or miss** (owed since #900). Tag the
   journey with the hit, so `game_usable` and `dashboard_usable` can be split
   and the 200 ms revisit target checked.
3. **A hit doesn't say whether a prefetch filled it.** Add a flag to
   `data_cache_hit`, so the prefetch-used rate is a number, not an upper bound.
4. **`mongo_query` doesn't separate checking a connection out from running the
   command.** Time the pool checkout as its own span (the driver's
   `connectionCheckOutStarted` / `connectionCheckedOut` events), so the
   slow first query after idle can be attributed.
5. **Board vitals don't name the renderer.** Add the SVG or 3D board to the
   board's region, or take the next board-vitals reading from a build after #915.
6. **The build list reaches back only ten deploys.** In a busy week that's less
   than the window. Let the screen take any build time, or offer "first build
   after `since`", so the next checkpoint can filter by build from the UI.

## Recommended next steps

In order of what they save, cheapest first where it's close:

1. **Find and remove the cold home wait** (about 4 s on every cold home open).
   Instrument the confirmation first (gap 1), then fix what it shows.
2. **Renew the session before a foreground refetch** rather than after a 401
   (3.4 s on 15% of board polls).
3. **Serve stale names and refresh them after the response**, with a longer
   hard expiry (about 245 ms on every `entry`).
4. **Attribute the first query after idle** (gap 4), then decide whether a
   cheap ping on resume, or different pool settings, removes it.
5. **CLS in the turn sheet's sections and on `/`** (Phase 3.9).
6. **Board INP on the 3D board** (Phase 3.10), profiled for paint cost.

The cold-instance platform cost (about 2.2 s at p75) and the shell render
after a deploy are left as they are. Neither has a fix in code that pays for
itself at this traffic.
