## The first reads on a new instance (likely)

Board `entry` (n=9): `mongo_connect` 203 ms, `mongo_checkout` 0 ms, and
`mongo_query` 1,688 ms (p75 1,813) for one indexed `findOne` that takes 14 ms on
`refresh`. 7 of the 9 were on a new instance.

- `dbConnect` (`src/utils/mongodb/mongodb.ts`) leaves Mongoose's `autoCreate`
  and `autoIndex` at their defaults, which are on. Each of about twenty
  top-level models calls `Model.init()` when it is compiled. Once the
  connection is open, each sends `createCollection` and then one `createIndex`
  per declared index.
- About twenty commands at once grow the pool to about twenty connections,
  three handshakes at a time (`maxConnecting: 3`). A handshake takes 71 ms at
  the median when one is reported. The request's reads wait in the same queue.
- **Why `mongo_checkout` doesn't show the wait:** the driver serves its wait
  queue from whichever async context frees or opens a connection. During
  start-up that is the index work, which runs in no request's store, so the
  waits are credited to no request. That is also why `mongo_handshake` never
  appears on `entry`. The dashboard's p75 checkout of 1,450 ms is where some of
  it does land.
- This is consistent with every span, but it hasn't been reproduced: there is
  no production-shaped database to try it against. The next checkpoint proves
  or disproves it (see "What to read next time").

## What to read next time

The changes made after this checkpoint, and what proves them
([plan: "Cold instances"](../loading-performance-plan.md#cold-instances)):

1. **Indexes built at deploy time, not by every new instance.** On `entry`:
   `server_mongo_query` should fall from about 1.6 s towards tens of
   milliseconds, `server_kb_worlds` with it, and `mongo_checkout`'s p75 should
   drop. If `mongo_query` stays above about 500 ms on `server_instance_new`
   requests, the hypothesis is wrong and the first-read cost lies elsewhere
   (cold JavaScript, server selection).
2. **A warm-up ping while Clerk loads.** `api_warm` and the `warm` request tag
   say how long the ping took and whether it found a new instance. On `entry`,
   `server_instance_new` should become rarer, or report an instance age close
   to the ping's lead, which means the ping got there first. `api_network` on
   `entry` should fall from 2.55 s towards the warm 150–250 ms. If the ping's
   instance is new but the `entry` that follows it is on a new instance too,
   the platform isn't routing the request to the warmed instance.

## Recommended next steps

1. Take Mongoose's start-up index and collection work off the request path,
   with a deploy-time index sync (likely 1.5 s on every cold open).
2. Wake the API's function while Clerk loads (up to 1.5 s of the 2.55 s
   platform start on every cold open).
3. Keep player display names in a store shared by instances (about 250 ms on
   every cold open), once 1 and 2 are measured.
4. Fix CLS in the turn sheet's sections and on `/` (Phase 3.9).
5. Not now: an idle prefetch (intent prefetch is already fully used), more
   static routes (every route opened cold is already static), and board INP
   (met on the 3D board).
